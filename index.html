01 · posição

Complexidade boa é a que tem um motivo para existir.

O guia começa com fundamentos e adiciona distribuição, observabilidade, segurança e operação quando o problema pede. O mesmo princípio vale para o fluxo de trabalho: cada issue acumula contexto suficiente para ser executada, testada e validada sem perder a intenção original.

BASE → CRESCIMENTO → AVANÇADOaprender o essencial antes de pagar o custo da complexidade
02 · o objeto de trabalho

A issue acompanha a ideia até ela virar evidência.

O ciclo único mantém negócio, técnica, IA e qualidade na mesma linha de rastreabilidade. A ferramenta pode mudar no caminho. O contrato de trabalho permanece.

A branch muda de contexto. A decisão continua registrada.
FALLBACK · QA REPROVADO

Falhar aqui não encerra o ciclo. Redireciona o ciclo.

O QA bloqueia a promoção para main, comenta a evidência na issue e devolve a mudança para a especificação que ficou incompleta.

ISSUE LEDGER

A issue guarda cada tentativa.

Comentário não é burocracia: é a memória de por que a solução mudou e qual evidência liberou o próximo passo.

04 · routing de IA

Trocar de modelo sem perder o projeto.

O esforço cognitivo é uma tag de roteamento, não um julgamento sobre a pessoa. O modelo recebe o contexto, os limites, os testes e o critério de aceite.

05 · arquitetura e qualidade

Vocabulário para decidir melhor.

Gangue dos Quatro, Clean Code e Clean Architecture entram como referências de pensamento. Metodologia ágil entra como mecanismo de feedback, priorização e entrega.

AGILE
METHOD

Agile é o ritmo de aprendizado do ciclo.

O PO descreve o valor, a issue guarda o contexto, a engenharia explicita as decisões, a pipeline produz evidência e o QA verifica o comportamento antes de o PO autorizar produção.

07 · princípios SOLID

Clique no princípio. Leia o contrato.

SOLID entra como instrumento de decisão: ajuda a encontrar o eixo de mudança, definir fronteiras e testar substituição sem virar checklist mecânico.

08 · Clean Code

Princípios para o código continuar legível.

Uma seleção operacional para revisão e implementação: intenção clara, limites pequenos, testes como documentação e mudança proporcional ao risco.

09 · refactoring

Detectar o cheiro. Fazer uma mudança pequena.

Code smells são sinais, não sentenças. As técnicas servem para reduzir custo de mudança com testes verdes e uma justificativa registrada na issue.

10 · antes de arquivar

O produto segue. O processo aprende.

Depois da produção, agentes especializados leem o histórico da issue e deixam um relatório pronto para virar uma nova issue, um ADR ou um commit do principal engineer.

11 · artefatos do harness

O método deixa material reutilizável.

Prompt de negócio, especificação técnica, possível entrega em código e relatório de melhoria: tudo pode ser copiado, versionado e usado na próxima issue.

12 · como ensinar cada conceito

Problema, solução, aplicação e limites no mesmo lugar.

A leitura usa uma estrutura inspirada no Refactoring.Guru: começar pelo sintoma, mostrar a solução, apresentar um exemplo pequeno, explicar como aplicar e fechar com trade-offs e relações. A referência é um modelo de clareza, não uma fonte para copiar conteúdo.
